## 0. 结论先行

**推荐方案 A 变体：忠实移植本地战场实例——只做原版单机本来就开着的四个本地 PVE 战场（1001 黄巾之乱 / 3001 十常侍之乱 / 5001 千里走单骑 / 8001 凤仪亭），官渡 / 讨伐董卓照原版保持关闭，6001/9001 跨服与 11000 赤壁明确不做。** 理由：本地战场的服务端逻辑 100% 存在于单机包内且原版单机可玩，这不是"发明单机语义"，而是补齐原版单机本来就有的最后一块玩法；战斗回合引擎、行军 Tick、任务、排行、勋章等周边已全部就位，动刀点只剩三块。

### 2.2 ChibiBattle（赤壁客户端）——1244 个 .as

计数：**1244 个 .as，共约 20.5 万行**；573 个是框架（mx 419 + Cairngorm + joyport IOC/DSS），**真实游戏类 410 个**（去框架后约 8.0 万行）。

结构：Cairngorm MVC（command/model/event/viewhelper），本质是一个**自带的"迷你三国城池游戏"**：

- 独立内城：`view/interior/building/*` 官府/兵营/校场/仓库/市场全套（建造/升级/拆毁、征兵 `ArmyDraftPanel`、校场出征/战术/俘虏/流民/伤兵 `forceyard/*`）；

## 3. 单机语义选项对比

工作量倍数以阶段 5（世界与战斗，7 周）为基准。阶段 5 的 PHP 面约 5,800 行（TroopFunc 688 + WorldFunc 1032 + GroundFunc 1608 + cfg_js 战斗部 + ReportCron 684）+ 客户端 35 类/63,460 行。

### 方案 A：本地战场实例（服务端起房间，玩家与 NPC 按原规则打）

忠实移植 BattleFunc.php 的本地部分：`createBattle` 生成战场（cfg_battle_city → sys_battle_city + cfg_battle_troop → NPC 驻军 sys_troops state=4）、`joinToBattle/joinToPVPBattle` 进场（NPC 阵营照 cfg_battle_union 14 行）、战场内行军/攻击/增援/召军（sys_troops task 7/8/9 → troop.tick 战场分支 → mem_battle type 4 → OldBattleService）、据点探索与事件（questInCity + cfg_battle_event）、功勋/勋章/商店/排行周边。双账号可同场（maxpeople 5）。

- **工作量**：≈ 阶段 5 的 **1.2–1.4 倍（8–10 周）**。PHP 面 4,529 行（BattleFunc 全量）+ HandleTroop 战场分支约 250 行 + 事件系统；客户端去框架 7.4 万行、UI 约 70 类。若按 2.5 节变体只开四个 PVE 战场（官渡/讨伐董卓保持关闭），可压到 **7–8 周**（原计划给阶段 9 的 7 周原本含赤壁与跨服，砍掉后反而贴得住）。
- **动刀点**：①新 battlefield 命令模块（52 条命令）；②troop.tick.ts 战场分支（task 7/8/9 + resetBattleFieldUid + winpoint）；③battle-result.ts 战场终局（事件/增援/勋章结算，桩已留）；④push proc 53（可选，等待队列通知）。**无新 DB 表**。
- **风险**：cfg_battle_event 1,014 行触发器语义（增兵/消失将领/任务/胜负四种 target）与官渡军粮规则最绕——但全程本地可差分兜底；BloodBattle UI 无 `legacy/ui/BloodBattle` 提纲（legacy/ui 只有 BloodWar），布局要从反编译 AS 抄（MXML 展开后可读性差，BattleChoiceDialog 7,716 行）；`mx.charts` 趋势图需自绘简化或降级为表格。
- **砍掉**：6001/9001 跨服房间（跨服排行/孟获积分/房间聊天）、11000 赤壁、沙场；趋势图数据退化为本地数据。

### 方案 B：仅 NPC 单人挑战（砍多方势力与同盟）

只开 1001 一个战场、单人场（人数校验改写）、砍 joinToBattle/invite/援军/召军/两阵营 winpoint，NPC 据点照 cfg_battle_troop 打。

- **工作量**：≈ 阶段 5 的 **0.6–0.8 倍（4.5–5.5 周）**。命令砍到约 30 条，但 UI 大头（战场地图/出征/攻击/探索/任务/商店，约 40 类）一样要做。
- **动刀点**：同 A，另需改写 createBattle/joinToBattle 的人数、阵营、军粮校验——每处简化都是一个要记录的"有意为之"分叉。
- **风险**：与原版语义分叉最多；将来升级到 A 时 createBattle 与结算两处返工；可差分对照的命令面变少（joinToBattle/invite/援军无对照），**差分保障反而下降**。
- **砍掉**：组队/邀请/援军/召军、官渡+讨伐董卓、凤仪亭主线联动、跨服、赤壁。省下的主要是三条纯本地逻辑线，而 UI 成本几乎不省。

### 方案 C：裁剪不做（保留周边，入口显示关闭文案）

战场入口（TopPanel battle 视图）显示关闭文案；保留已就绪的周边：rank_battle_* 排行（已接、空榜）、战场周奖励（已接）、勋章（已接）；再补 8–10 条大厅查询（getBattleInfo/getUserBattleInfo/getBattleTime/getBattleActiveState/getBattleNews/getBattleInfor/getBattleNetUrl 返回空 + getMedalExchangeInfo）让顶栏战况不报错。

- **工作量**：≈ 阶段 5 的 **0.05–0.1 倍（2–4 天）**。
- **动刀点**：无表改动；客户端一个占位视图；差分 6–10 组。
- **风险**：最低。与原版对照：跨服/赤壁在原版单机同样不可玩，行为一致；**但四个本地 PVE 在原版单机是可玩的——C 是唯一比原版单机还"退步"的选项**。
- **砍掉**：约 9.6 万行 UI 对应的全部战场玩法。

### 三案对比总表

| | A 本地战场实例 | B 仅 NPC 单人挑战 | C 裁剪不做 |
|---|---|---|---|

## 6. 一页决策摘要

**推荐：方案 A 变体——本地战场实例，只做原版单机就开着的四个本地 PVE 战场（1001/3001/5001/8001），官渡/讨伐董卓照原版关闭，6001/9001 跨服与 11000 赤壁不做。**

一句话理由：本地战场的 105 个服务端函数、11 张配置表、1,014 行事件触发器全在单机包内且原版单机可玩——这不是为单机发明降级语义，而是补齐原版单机本来就有的玩法；战斗引擎/行军 Tick/任务/排行/勋章/37 张表/入口按钮全部就位，真正要写的只有 52 条命令 + 行军战场分支 + 战场终局三块。

**三个关键数字**：

1. **BloodBattle 559 个 .as**（12.1 万行，去框架后真实游戏类 166 个/约 7.4 万行）；**ChibiBattle 1244 个 .as**（20.5 万行，去框架后真实游戏类 410 个/约 8.0 万行）。
2. **PHP 战场函数：BattleFunc.php 4,529 行 / 105 个函数**，其中 54 个在 openfunc 白名单（52 条未移植）；跨服桩 BattleNetFunc 4 + ChibiNet 1 + 回调 39，均范围外。
3. **白名单战场命令：约 58 条**（54 本地定义 + 3 条本地无定义的跨服死命令 + 1 条赤壁状态查询），openfunc 全表 530 条。

**工作量**：约 7–8 周（≈ 阶段 5 的 1.0–1.15 倍；原计划给阶段 9 的 7 周含赤壁与跨服，砍掉后贴得住）。方案 B（单人挑战）4.5–5.5 周但引入分叉且 UI 不省；方案 C（裁剪）2–4 天，是唯一比原版单机退步的选项。

**风险 Top3**：① cfg_battle_event 1,014 行触发器与官渡 winpoint 语义（差分兜底）；② BloodBattle UI 无 legacy/ui 提纲，布局需从反编译 AS 反推（阶段 8 已有同流程经验）；③ mx.charts 趋势图需降级实现。

**明确不做**：跨服（getBattleNetUrl 返回空一行实现）、赤壁（服务端缺失，判"原版不可达"）、沙场（阶段 8 判例）。
